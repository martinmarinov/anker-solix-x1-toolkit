Anker SOLIX X1: the 1-hour TOU limit is in the slider, not the protocol

A breakdown of how the Anker app talks to the X1 over the Anker cloud, what the Time-of-Use payload actually looks like, and the cheapest safe way to get a 23:30–05:30 schedule.

Target X1 / X1-H · model codes redacted Engine Flutter Dart 3.11.0 AOT Transport HTTPS JSON + MQTT + Modbus TCP Method blutter + string-table analysis
This page predates the verified write and MQTT work; see REPORT.md §11–17 for the proven write payload, live telemetry, encryption findings and the gadget capture method.
Verdict

The app sends start_time_period and end_time_period as “HH:mm” strings, and its serializer copies them into the JSON verbatim — no division by 60, no rounding. The 1-hour step comes from a 24-tick slider in the Flutter UI. A 23:30 boundary is expressible on the wire.

Already proven in the field: a 23:30–05:30 window ran on real hardware via the Dynamic Tariff path (Anker case #TNJ909651061). The inverter is half-hour capable. What remains is whether the Time-of-Use endpoint accepts the same values — a config write with snapshot and rollback, not a firmware change.

Hard requirement for the final build

Reproduce the Time-of-Use editor — never replace the controller

  1. Ride the target-driven TOU controller. Write the TOU rate plan and keep the system in Time of Use mode. That controller computes a rate to reach the target by the end of the valley window — which is why it ramps and modulates instead of slamming to 6 kW.
  2. Never use the Dynamic Tariff / window-driven scheduler. No save_dynamic_price, no charging_hes_dynamic_price_svc/*, no mode flip.
  3. Never send a charge-power value. The TOU payload has no power field; inventing one means driving a different controller. Describe when and which tariff; let the EMS derive how fast.
  4. Change only the boundaries. Mode, price_type, seasons, day_type, peak_type, prices and energy_unit are copied verbatim. The tool's assert_times_only() refuses anything else.
  5. Mirror the screen, with 30-minute steps as the only difference: same “Jan – Dec” season, same Weekday/Weekend split, same period rows (type + start + end + price), same add/remove capped at 4 periods, same Save. 48 slots instead of 24.
  6. If :30 is ever rejected on the TOU path — stop. Do not switch to Dynamic Tariff to get granularity; that trades a UI bug for an overcurrent hazard.

Acceptance: read-back differs only in the two time fields · app still shows Time of Use · charge power ramps (first ~10 min below steady state) · grid draw stays under the configured ceiling with backup load present.

03What a Time-of-Use plan really looks like

Recovered from peak_valley_param_data.dart and the X1 device-command model. Your “Jan – Dec / Weekday / Super Off-Peak / Peak” screen maps 1:1 onto it:

  "peak_sessions": [{
    "start_time": "2026-01-01 00:00:00",   // the "Jan - Dec" season
    "end_time":   "2026-12-01 00:00:00",
    "peak_valley_prices": [
      { "start_time_period": "23:30",   // ← minutes live here
        "end_time_period":   "05:30",
        "peak_type": 1,        // cheapest→dearest: 1 Super Off-Peak … 4 Peak
        "day_type":  1,        // 1 Weekday · 2 Weekend

  }],

Three independent proofs that the hour is UI-only

Proof 1 · serializer
Verbatim copy
PeakValleyPrices.toJson loads field_17 / field_1b and writes them straight into the map. No arithmetic anywhere.
Proof 2 · literal
Quoted template
The app builds {"start_time":"…" — a string. An hour-integer API would serialise as {"start_time":5.
Proof 3 · sentinel
"23:59"
End-of-day is clamped to 23:59, not 24. The schema thinks in minutes.
Where the hour actually comes from: the custom vertical range slider on the “Jan – Dec” screen — 24 ticks labelled 00/06/12/18/24, always rendering :00. Adjacent localised strings include German “Stunde einstellen” (“set the hour”).

04Field evidence — and why Anker's workaround is unsafe

Anker support's reply to “can TOU be 30 minutes?” was: use Dynamic Tariff instead. That is a non-answer to the question, but it is a decisive data point for the reverse engineering — and it carries a safety finding.

What it proves
Half-hours work on the hardware
On app v3.14.0 the Dynamic Tariff feature held a 23:30 → 05:30 charge window. So the cloud accepts :30 and the inverter executes it. The main unknown is closed: the 1-hour step belongs to one picker widget, nothing else.
What it costs
A real overcurrent event
In that mode the X1 charged at a flat 6 kW with no regard for the rest of the supply. With ~2 kW of backup load it pulled a bit over 8 kW (6 kW charge + ~2 kW backup) through a 32 A breaker (≈7.4 kW) for over an hour until it tripped, taking the X1 off grid and needing a manual reset.
The mechanism matters: in Time of Use / Super Off-Peak the unit modulates charge power to stay within rated current regardless of backup load. Dynamic Tariff does not. So the goal is to change the times while keeping the mode — never to switch mode to obtain half-hour slots.
Consequences for the build: (1) Dynamic Tariff is excluded on safety grounds, not just tariff mismatch. (2) Write the TOU rate plan and keep mode = Time of Use. (3) Set a grid import / charge power limit below the breaker rating as defence in depth — then a bad schedule trips a limit, not the breaker. (4) Verify the first cycle with current, not just timestamps.

05Can you cap charge power today?

Yes — the controls already ship in the app. This matters more than the 30-minute feature: a hard ceiling is what makes any schedule experiment safe.

Where it actually is (verified on device)
Settings → Modes → Advanced Options
Grid Charging is a plain on/off switch at the bottom of the Modes page (currently on), next to Peak Shaving. The row is not clickable — there is no detail page — and no kW ceiling is exposed in the consumer app.
What the code suggests vs. reality
AE100, not X1
station_power_limit_model (ac_input_power, legal_power_limit) belongs to the AE100 / station family. For this X1, /site/get_power_limit returns data: null. The ceiling must be set by the installer in Anker SOLIX Professional.
Set it before anything else. Your 32 A breaker is ≈7.36 kW at 230 V. 6 kW of charge plus ~2 kW of backup load ≈ 8 kW. A ceiling of ≤4.2 kW — Anker's own example value — leaves ~3.2 kW of headroom and would have prevented the 29 Nov trip on its own.
Necessary, not sufficient: it is not established that Dynamic Tariff honours acPowerLimit. Treat the ceiling as defence in depth, not as permission to use the unsafe mode. The new tool will read it, print it on every run, and refuse to write a schedule while it is missing or above a configured maximum.

06Why TOU paces and Dynamic Tariff slams

They are different schedulers, not one scheduler with a hidden power parameter.

Time of UseDynamic Tariff
You supplya price map over valley/peak windowsexplicit charging windows + cutoff SOC
Controller solvesreach the target by the end of the window — an energy problem charge while this window is open — a state problem
Resulting powercomputed rate, ramped, modulated against house load saturates at max immediately
Load awareyes (observed)apparently not (observed: 6 kW + 2 kW)
The payload proves the app isn't choosing a hidden power. The X1 TOU object contains only times, peak_type, day_type, buy and energy_unit — no power field exists. So the pacing is computed downstream by the cloud EMS / firmware. It is a control law, not a parameter.
The tell is the missing ramp. A target-driven controller knows how many kWh it needs and how long is left, so it starts gently and holds a rate. A window-driven controller has no reason to ramp: the window says “charge”, the cutoff says “until full”, and the only brake is a power ceiling. That is exactly the behaviour you observed.
Why this is good news for the build: writing the TOU plan means we never have to reproduce a power computation — the cloud does it. Keeping mode = TOU preserves the pacing, and a 6-hour window needs less average power than the 5-hour one, so it should be gentler still. Still unknown: whether acPowerLimit binds inside Dynamic Tariff, and whether the EMS recomputes its rate for an externally written plan (the first cycle's current measurement answers it).

08Safety model

🟢 Safe
Reads
Site list, device list, plan, energy stats. Do freely.
🟡 Controlled
Rate-plan write
Snapshot first, change only the two time strings, read back, roll back on mismatch.
🔴 Avoid
Everything else
OTA/firmware, power-cutoff, Modbus toggles, unknown cmd values, mode/SOC changes.
Reality check
Not firmware — but still electrical
No bricking path: a plan is configuration. But a schedule also selects how the unit charges, and one of those modes already tripped a 32 A breaker here. Treat charge-control changes as electrical, not merely behavioural.
Two hard rules: never switch mode to Dynamic Tariff to obtain half-hour slots; and set a grid import / charge power limit below the breaker rating before the first experiment, so a bad schedule trips a limit rather than the breaker.
The other real trap: cmd. The app uses 17, 123 (HES TOU) and 0 on different paths, while the public library sends 17 everywhere. Never guess it — capture your app's own Save request (mitmproxy, or Frida if pinning appears) and replay that exact shape.

10What remains unknown

  • Whether the Time-of-Use endpoint accepts :30 — same encoding as the Dynamic Tariff path that already worked, but a different service. This is the remaining test.
  • Whether load-aware charge modulation is preserved when the plan is written by a third-party client (it should be, since mode stays TOU — verify on the first cycle).
  • The exact cmd your firmware expects (17 vs 123 vs 0) — capture it.
  • Whether your installer can enable Modbus (Ethernet run, single inverter).
  • Endpoint stability across app releases — param_type 9 was removed in Jul 2025.
Full detail, evidence index and the reference client: REPORT.md · poc/anker_tou.py. Anker provides no public cloud API; the only sanctioned third-party interface is local Modbus TCP. Use your own credentials, don't share them, and prefer Modbus where it can do the job.
